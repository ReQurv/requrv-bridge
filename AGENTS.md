# AGENTS.md

Tauri 2 + Nuxt 4 desktop app that launches AI coding agents (OpenCode, Codex, Claude Code, Hermes) pre-configured for the AI Hive gateway. Frontend in `app/`, Rust backend in `src-tauri/`.

Open source (GPL-3.0-or-later). To add a new agent connector, follow the step-by-step guide in [CONTRIBUTING.md](./CONTRIBUTING.md).

## Commands

- Use **Bun** exclusively (`packageManager` is bun; CI runs `bun install --frozen-lockfile`).
- `bun install` first — `postinstall` runs `nuxt prepare`, which generates `.nuxt/`; `lint` and `typecheck` fail without it (ESLint imports its base config from `.nuxt/eslint.config.mjs`).
- `bun run tauri dev` — full app (Nuxt on :3001 + Tauri window).
- `bun run build:mac` — signed + notarized macOS release build. Sources the gitignored `.env` (`APPLE_ID`, `APPLE_PASSWORD` app-specific, `APPLE_TEAM_ID`) into the real process env — required because Bun's automatic `.env` loading is invisible to the N-API Rust CLI (`getenv`). The signing identity is pinned in `src-tauri/tauri.conf.json` (`bundle.macOS.signingIdentity`); keep it in sync with the Developer ID certificate.
- `bun run dev` — web-only dev; Tauri features auto-degrade.
- `bun run lint`, `bun run typecheck` — what CI runs for the frontend (`.github/workflows/ci.yml`). There is no JS test suite.
- Rust tests: `cargo test` from `src-tauri/` (unit tests live in `src-tauri/src/commands.rs`). CI also runs `cargo clippy -- -D warnings`.
- **After every change, build the app and report the artifact path.** Run `bun run tauri build --no-bundle` (works without signing credentials; `--no-bundle` skips the Developer ID step and yields the release binary) and give the user the path — by default `src-tauri/target/release/app`. Use `bun run build:mac` only when a Developer ID certificate is in the keychain and `.env` holds the notarization credentials: `bundle.macOS.signingIdentity` is pinned in `src-tauri/tauri.conf.json` and the build fails without it.

## Architecture

- Single page (`app/pages/index.vue`) + `app/composables/useHive.ts` wrapping all `invoke()` calls. All backend logic is in `src-tauri/src/commands.rs`; commands are registered in `lib.rs`.
- Nuxt is SSG (`ssr: false`); the app source dir is `app/` (Nuxt 4 layout), not a root-level `pages/`.
- Frontend detects Tauri at runtime via `__TAURI_INTERNALS__` (`useHive.ts`) and must keep working in plain web mode — follow this guard when adding `invoke` calls.
- Tauri dev server is pinned to port 3001 (`strictPort` in `nuxt.config.ts`, `devUrl` in `tauri.conf.json`). Don't change one without the other.
- `nuxt.config.ts` ignores `**/src-tauri/**` (EMFILE watch workaround) — don't remove.
- Hive key is stored as plaintext `hive.json` in the Tauri app config dir (`.bak` written before overwrite); model list comes from `GET https://hive.requrv.ai/api/v1/models`.
- Launch flows: OpenCode gets a `requrv-hive` provider merged into `~/.config/opencode/opencode.jsonc` (existing fields preserved, JSONC comments stripped) and is detected/restored via `opencode_configured_in`/`restore_opencode` (`.bak` backup taken once, only while the file is not already ours). The known model entry pins `variants` (`high` disabled, `xhigh` added) because OpenCode's default thinking ladder is low/medium/high: the gateway rejects `high` with 502 Bad Gateway and accepts `xhigh`, which the ladder omits. The desktop app reads that file only at startup, so it is configured by a frontend-driven flow (`configure_opencode_app` → restart confirmation → `restart_opencode_app`/`open_opencode_app`) and `launch_service` does NOT handle `("opencode","app")` on purpose; the CLI still goes through `launch_service`.
- Every integration that writes something is **persistent** and restorable, model after model and after Bridge's exit: OpenCode (`opencode.jsonc`), Claude Code (`~/.claude/settings.json`), Codex (shared `~/.codex/config.toml`). Only env-only targets (Hermes) have no restore. A key change (`set_hive_key`) calls `reapply_persisted_configs`, which rewrites every already-configured target so the key on disk cannot diverge from the app's; failures are reported to the user while the key stays saved.
- Claude Code is terminal-only: the gateway env vars (`ANTHROPIC_BASE_URL` = `HIVE_ANTHROPIC_BASE_URL` — note it's the gateway **without** the trailing `/v1`, because the client appends `/v1/messages` — plus `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS` pinned per model (200k for requrv-small-3.8, 128k default)) are exported to the launched process **and** merged into the `env` block of `~/.claude/settings.json` (`write_claude_code_settings_in`), which is the authoritative source because the client applies that file over the process environment — this is what makes the configuration survive the launcher. The merge is conservative (all other top-level keys and non-Hive `env` entries survive, an invalid JSON file is never overwritten) and `ANTHROPIC_AUTH_TOKEN` is blanked because settings files are merged, not replaced, and a leftover token would be sent as a Bearer header instead of `ANTHROPIC_API_KEY`. Backup `settings.json.hive.bak`, restore via `restore_claude_code_cli`. The `/messages` probe gate still applies (Anthropic Messages API; the gateway must also accept `role:"system"` in `messages[]`, which Claude Code v2.x sends).
- ChatGPT.app (macOS) and the Codex CLI share **one** configuration: both go through `configure_chatgpt_app_in`, so `launch_codex_cli` writes `~/.codex/config.toml` (+ `~/.codex/hive-models.json`, `auth.json`) and starts `codex` with `CODEX_HOME` pinned to `~/.codex` and no other environment (the provider table authenticates both surfaces with `experimental_bearer_token`; there is deliberately no `env_key`, because codex refuses to start with "Missing environment variable" when the declared variable is absent — which breaks a hand-typed `codex` and the app). The same `CODEX_HOME` pin is applied when opening ChatGPT.app: `open` and the spawned shell forward the caller's environment, so a `CODEX_HOME` inherited from the shell that started the bridge (e.g. an editor-managed codex runtime) would otherwise send both surfaces to a config this launcher never wrote. A `codex` typed by hand therefore uses AI Hive too; the legacy `hive.config.toml` / `hive.config.bak` / `hive-cli-models.json` are gone and `restore_chatgpt_app_in` deletes them if a previous version left them. ChatGPT.app is configured by a frontend-driven flow (`configure_chatgpt_app` → restart confirmation → `restart_chatgpt_app`/`open_chatgpt_app`): it rewrites the root of `~/.codex/config.toml` (`model`, `model_provider = "requrv-hive"`, `model_catalog_json` → `~/.codex/hive-models.json`, other keys preserved via the `toml` crate) plus a `[model_providers.requrv-hive]` table (`base_url` = Hive, `wire_api = "responses"`, `supports_websockets = false`, key in `experimental_bearer_token`), sets `~/.codex/auth.json` to apikey mode with the Hive key, keeps one-shot `.hive.bak` backups of both and can fully restore them (`restore_chatgpt_app`, never touches a ChatGPT OAuth auth). The custom provider is mandatory: ChatGPT.app 26.x (Codex core ≥ 0.154) defauefaults the Responses transport to WebSocket, which the Hive gateway does not implement — built-in providers cannot be overridden, and custom providers ignore `auth.json` (hence the bearer token). Older installs used a root `openai_base_url` instead; detection/restore still recognize and clean that legacy shape. The app reads its model catalog at startup, so a running instance needs the restart confirmation; `launch_service` does NOT handle `("codex","app")` on purpose. The catalog is parsed strictly against the codex `ModelInfo` schema: `supported_reasoning_levels` must be `{effort, description}` objects (plain strings fail the parse), `input_modalities` only accepts `text`/`image`/`audio` (Hive's `video` is dropped), and the app-server re-reads `config.toml`+catalog on every request, so a fixed catalog is picked up without restart.
- Hermes Agent (hermes-agent.nousresearch.com) ships two surfaces, both configured with environment variables only — nothing is persisted, so there is no restore. The **desktop app** takes no `--provider` flag, so it is launched like the ChatGPT.app flow (frontend-driven `launch_hermes_app`/`restart_hermes_app`; `launch_service` does NOT handle `("hermes","app")`) with `CUSTOM_BASE_URL` = `HIVE_OPENAI_BASE_URL` (redirects the configured custom provider) + `OPENAI_BASE_URL` (same, so `OPENAI_API_KEY` becomes the key for that endpoint) + `HERMES_INFERENCE_MODEL`, after probing `/chat/completions`; an already-running instance needs the restart confirmation (the spawned Python backend inherits the app's `process.env`). Those vars only take effect while `~/.hermes/config.yaml` resolves to the custom/openai-compatible path — a config on another provider (e.g. `nous`) ignores them. The **CLI** (`hermes`, written by install.sh to `~/.local/bin`) is handled by `launch_service` `("hermes","terminal")` → `launch_hermes_cli`, which pins `--provider openai-api -m <model>` and passes `OPENAI_BASE_URL` (= `HIVE_OPENAI_BASE_URL`) + `OPENAI_API_KEY` — explicit and independent of the configured provider — after probing `/chat/completions`. Neither surface reads or writes `~/.hermes/config.yaml`. Detection: the app is any `*.app` containing "hermes" in `/Applications`/`~/Applications` (macOS) or `HERMES-IDE`/`hermes-ide` on PATH elsewhere; the CLI is `hermes` on PATH or `~/.local/bin/hermes` (`%HERMES_HOME%`/`%LOCALAPPDATA%` venv on Windows). On macOS the app's inner Mach-O (`CFBundleExecutable` via `plutil`, fallback: first file in `Contents/MacOS`) is spawned detached with the env, and the running-app probe matches the bundle executable name `Hermes`.
- Claude Desktop (Code tab) cannot be pointed at AI Hive and is intentionally NOT supported: the consumer app's Code tab runs cloud sessions authenticated with the claude.ai account (`CLAUDE_CODE_OAUTH_TOKEN`, subscription-scoped model catalog), launches its SDK with empty setting sources (ignores `~/.claude/settings.json`), and custom gateways are an enterprise-only ("3p") feature disabled in this build. Claude Code detection therefore counts the CLI only.

## Conventions

- User-facing strings (Rust error messages, UI copy, toasts) are in **Italian** — keep new user-facing text in Italian.
- Rust code is indented with **2 spaces** (matches `.editorconfig`); do NOT run `cargo fmt` — it would reformat everything to 4 spaces.
- Frontend style is enforced by ESLint (`@nuxt/eslint` stylistic): no semicolons, single quotes, 2 spaces, no trailing commas. There is a `.prettierrc` but no format script; `bun run lint` is the check.
- Version is duplicated in `src-tauri/tauri.conf.json` and `src-tauri/Cargo.toml` — bump both together. Releases are automatic: pushing a `v*` tag triggers `.github/workflows/build.yml` (tauri-action builds macos/linux/windows and publishes a GitHub Release; the tag comes from the version in `tauri.conf.json`).
